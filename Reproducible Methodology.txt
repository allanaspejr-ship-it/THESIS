REPRODUCIBLE METHODOLOGY FOR THE RBFNN HYDROPOWER FORECASTING MODEL

This note documents the RBFNN design, training, tuning, and evaluation procedure used in the thesis forecasting workflow. It is intended to make the RBFNN results reproducible from the cleaned data, scripts, model artifacts, and metadata saved in the project folder.

2. Plant-specific modeling strategy

A separate RBFNN model is trained for each Agus hydropower plant:

- agus1
- agus2
- agus4
- agus5
- agus6
- agus7

Each model predicts the next-hour change in plant generation, not the generation level directly. The final generation forecast is reconstructed from the latest known generation value plus the predicted residual/delta.

For each plant:

target = total_gen_<plant>
next-hour generation = total_gen_<plant> shifted by -1 hour
residual/delta target = total_gen_<plant>_tplus1 - total_gen_<plant>

This residual/delta target is saved in the feature table as:

total_gen_<plant>_delta_tplus1

The purpose of this formulation is to anchor the forecast to persistence and let the RBFNN learn changes around the latest known operating level.

3. Chronological data split

The cleaned hourly data is split chronologically, not randomly:

- 70 percent training
- 15 percent validation
- 15 percent testing

The training split is used to fit the model weights and scalers.
The validation split is used for model selection and calibration.
The testing split is reserved for final reporting only.

No testing rows are used for selecting RBF centers, learning rates, shrinkage, bias correction, calibration, or profile adjustments.

4. Feature construction

The RBFNN feature set is generated in cell2_rbfnn.py by add_features() and feature_columns_for().

Feature families include:

- calendar and time-of-day features
- target-hour sine/cosine features
- lagged generation values
- rolling generation statistics
- generation differences
- unit generation share features
- outage/status features available before the forecast time
- lagged rainfall and hydrologic context
- upstream cascade features

The model uses leakage checks to prevent target, forecast, actual, testing, validation, or future columns from entering the feature list.

The feature leakage audit is saved in:

- Thesis Forecasting/metadata/leakage_audit.json

5. Scaling

The input features are scaled using StandardScaler fitted on the training split only.

The residual/delta target is also scaled using StandardScaler fitted on the training split only.

Saved scalers:

- Thesis Forecasting/models/rbfnn/x_scaler_<plant>.pkl
- Thesis Forecasting/models/rbfnn/y_scaler_<plant>.pkl

Validation, testing, and day-ahead backtesting reuse these training-fitted scalers.

6. RBFNN architecture

The RBFNN is implemented with:

- Input layer matching the plant-specific feature count
- Gaussian radial basis hidden layer
- Linear output layer for the scaled residual/delta prediction

The RBF hidden layer computes Gaussian activations based on squared distance from learned centers.

The output layer predicts the scaled next-hour residual/delta.

The model is compiled with:

- optimizer: Adam
- loss: mean squared error

7. RBF center initialization

RBF centers are initialized using K-means clustering on the scaled training feature matrix.

The number of clusters is equal to the selected number of RBF centers, unless the training set has fewer rows than the requested center count.

The K-means random seed is fixed at 42.

The centers remain trainable during neural network training.

8. Hyperparameter search

The RBFNN hyperparameter search is defined in rbfnn_search_configs().

The searched settings include:

- number of RBF centers
- learning rate
- gamma initialization
- batch size
- early stopping patience

Base center counts and search values include:

- centers: 40, 60, 80, 120, 160, 180, 220
- learning rates: 0.0012, 0.0010, 0.0007, 0.0005, 0.0003, 0.0002
- gamma initial values: 0.5, 1.0, 2.0
- batch sizes: 16 and 32
- early stopping patience values: 8, 12, 16, 20, and 24 depending on the plant-specific configuration

Additional plant-specific candidate configurations are included for Agus 1, Agus 2, Agus 4, Agus 5, Agus 6, and Agus 7.

Training uses:

- maximum epochs: 80
- early stopping on validation loss
- restore_best_weights=True

9. Preliminary validation screening

For each candidate RBFNN configuration, the model predicts the validation residual/delta. The residual/delta prediction is reconstructed to generation level using:

predicted_generation = current_generation + shrinkage * predicted_delta + bias

Shrinkage is searched over:

- 0.05
- 0.10
- 0.20
- 0.35
- 0.50
- 0.75
- 1.00
- 1.15

The best preliminary candidates are ranked using a validation score that includes:

- operational MAPE
- RMSE
- R2
- an additional penalty for negative R2

The R2-aware score prevents selecting a model that has low percentage error but poor trend/shape behavior.

Only the top RBFNN finalists are passed into rolling day-ahead validation.

10. Shrinkage tuning

Shrinkage controls how much of the predicted residual/delta is applied to the current generation level.

The formula is:

raw_prediction = current_generation + shrinkage * predicted_delta

Shrinkage is selected using validation data only.

The purpose of shrinkage is to reduce excessive drift and keep recursive forecasts stable during 24-hour forecasting.

Detailed rule:

Let:

- y_t = latest known generation at time t
- delta_hat_t+1 = RBFNN-predicted next-hour residual/delta
- s = shrinkage factor
- y_hat_raw_t+1 = raw next-hour generation forecast

Then:

y_hat_raw_t+1 = y_t + s * delta_hat_t+1

The shrinkage factor s is searched over the fixed grid:

s in {0.05, 0.10, 0.20, 0.35, 0.50, 0.75, 1.00, 1.15}

For each candidate model and each shrinkage value, validation predictions are reconstructed to generation level and scored using the validation metric selection rule. The selected shrinkage is the one associated with the best validation-only candidate. Testing data are not used to choose shrinkage.

Interpretation:

- s = 1.00 applies the full predicted residual/delta.
- s < 1.00 dampens the residual/delta and makes the forecast closer to persistence.
- s > 1.00 allows a slightly stronger-than-predicted movement when validation supports it.

This is especially important in recursive 24-hour forecasting because an overly aggressive delta can accumulate error across the day.

11. Bias correction

After shrinkage is applied, a validation-only bias correction is computed.

The bias is the median validation residual:

bias = median(actual_generation - raw_prediction)

The bias is clipped to the plant operational threshold:

maximum absolute bias = max(1 MW, 1 percent of plant capacity)

This prevents unrealistically large bias adjustments.

Final one-step corrected level prediction:

prediction = current_generation + shrinkage * predicted_delta + bias

Detailed rule:

Let:

- a_i = actual validation generation for validation row i
- p_i_raw = raw validation prediction after shrinkage for validation row i
- b = bias correction in MW

The unbounded validation bias is:

b_raw = median(a_i - p_i_raw)

The bias is then clipped to the plant operational threshold:

threshold_plant = max(1 MW, 0.01 * plant_capacity_MW)

b = clip(b_raw, -threshold_plant, +threshold_plant)

The corrected prediction is:

y_hat_t+1 = clip(y_t + s * delta_hat_t+1 + b, 0, 1.05 * plant_capacity_MW)

The bias is derived only from validation residuals after a candidate shrinkage value is applied. The test split is never used to compute or adjust the bias.

Interpretation:

The bias correction removes a consistent median overforecast or underforecast observed in validation while preventing large artificial offsets. Median residual is used instead of mean residual to reduce sensitivity to outliers.

12. Capacity clipping

All plant-level forecasts are clipped to physically plausible limits:

minimum = 0 MW
maximum = 105 percent of plant installed capacity

Installed capacities used:

- Agus 1: 80.0 MW
- Agus 2: 180.0 MW
- Agus 4: 158.1 MW
- Agus 5: 55.0 MW
- Agus 6: 219.0 MW
- Agus 7: 54.0 MW

Capacity clipping is applied during validation, testing, and operational forecasting.

13. Validation-only calibration

After the base model, shrinkage, and bias are selected, additional calibration may be tuned using validation data only.

The calibration options include:

a. Value-bin calibration

Predictions are grouped into quantile bins based on either current generation or base prediction. Median residual correction is estimated per bin using validation data.

The correction is scaled using a validation-tuned scale factor.

Detailed value-bin formula:

Let:

- p_i = validation prediction after shrinkage and bias
- a_i = actual validation generation
- r_i = a_i - p_i = validation residual
- z_i = bin basis value
- B_k = kth quantile bin
- c_k = median residual correction for bin k
- alpha = correction scale

The bin basis z_i is either:

- current generation y_t, or
- base prediction p_i

depending on the selected calibration basis.

For each bin:

c_k = median(r_i for rows where z_i is in B_k)

For a new prediction p with basis value z belonging to bin B_k:

p_calibrated = p + alpha * c_k

Then:

p_calibrated = clip(p_calibrated, 0, 1.05 * plant_capacity_MW)

The number of bins is searched using validation quantile choices, and the correction scale alpha is searched over validation-only scale values. The candidate is accepted only when it improves the R2-aware rolling validation score. Testing data are not used.

Purpose:

Bin calibration corrects systematic errors that depend on the generation level. For example, the model may slightly overforecast at high generation levels and underforecast at mid-generation levels. Bin calibration captures this pattern using validation residuals only.

b. Hourly residual correction

Median residual corrections may be learned by forecast hour using validation data.

The correction scale is selected from a grid using validation performance.

Detailed hourly formula:

Let:

- h_i = forecast target hour for validation row i, from 1 to 24
- p_i = validation prediction before hourly correction
- a_i = actual validation generation
- r_i = a_i - p_i
- q_h = median residual for hour h
- beta = hourly correction scale

For each forecast hour h:

q_h = median(r_i for rows where h_i = h)

For a prediction at forecast hour h:

p_hourly = p + beta * q_h

Then:

p_hourly = clip(p_hourly, 0, 1.05 * plant_capacity_MW)

The correction scale beta is searched over:

beta in {0.00, 0.25, 0.50, 0.75, 1.00, 1.25}

The hourly residual correction is derived only from validation residuals. It is accepted only if validation scoring supports it. Testing data are not used.

Purpose:

Hourly correction accounts for systematic time-of-day forecast bias, such as repeatedly underforecasting evening peaks or overforecasting low-load hours.

c. Same-hour-yesterday profile blending

The forecast may be blended with the same-hour-yesterday generation profile if validation-only tuning shows improvement.

This is used only when the validation selection rule accepts it.

Formula:

Let:

- p = current model prediction
- y_lag24 = generation from the same hour on the previous day
- w = profile blend weight

Then:

p_blend = (1 - w) * p + w * y_lag24

Then:

p_blend = clip(p_blend, 0, 1.05 * plant_capacity_MW)

The blend weight w is searched using validation data only. The purpose is to borrow daily shape information when validation shows that the same-hour-yesterday profile improves the recursive 24-hour forecast.

d. Day-ahead profile blend

Saved day-ahead validation predictions may be used to tune a same-hour-yesterday profile blend. The metadata explicitly records that testing was not used:

testing_used_for_day_ahead_profile_blend = False

The report is saved in:

- Thesis Forecasting/metadata/rbfnn/rbfnn_day_ahead_profile_blend_report.xlsx

Important validation-only rule:

All calibration components listed above are derived from validation behavior only. They are not fitted on testing predictions, testing residuals, or testing labels. Testing remains a final evaluation split.

14. Rolling day-ahead validation selection

RBFNN finalists are not selected only by one-step validation prediction.

The finalists are evaluated using leakage-free rolling 24-hour day-ahead validation backtests.

For each validation day:

1. Use only historical data before 00:00 of the forecast day.
2. Build forecast features from history available up to 23:00 of the previous day.
3. Forecast hour 1.
4. Append the predicted hour to the history.
5. Rebuild recursive features for the next hour.
6. Continue until all 24 hours are predicted.
7. Use actual forecast-day generation only after prediction to compute metrics.

The RBFNN selected model is the candidate with the lowest R2-aware rolling validation score among screened finalists.

15. Leakage-free validation and testing procedure

The thesis validation and testing metrics are based on strict rolling 24-hour day-ahead backtesting, not simple one-step-ahead prediction.

Validation and testing simulate the real forecasting process:

- Forecast day D is predicted using only data available before day D.
- Actual generation from day D is not used as an input.
- Actual rainfall from day D is not used as an input.
- Actual Lake Lanao outflow or other hydrologic variables from day D are not used as inputs.
- Actual outage status from day D is not used as an input.
- Actual day-D values are used only after forecasting, for metric computation.

The evaluation type is recorded as:

rolling_24h_day_ahead_backtest

16. Capacity and outage-aware forecasting

Operational forecast mode uses the planned outage input workbook:

- Thesis Forecasting/outputs/outages_planning/Planned_Outages_Input.xlsx

Validation and testing backtests do not use actual forecast-day outage status. If archived planned outage schedules are unavailable for historical validation/testing dates, the latest known outage/status before the forecast day is used.

This rule is recorded as:

outage_input_type = last_known_outage_status_before_forecast_day

The model also validates unit-level consistency:

- units marked unavailable are forced to 0 MW
- unit generation is clipped to unit capacity
- plant totals must equal the sum of unit forecasts
- cascade total must equal the sum of plant totals

Capacity adjustment rule:

Each plant-level generation forecast is first clipped to the physical plant range:

p_clipped = clip(p_forecast, 0, 1.05 * plant_capacity_MW)

Then outage-aware availability is applied.

Let:

- C_base = available capacity from the latest known pre-forecast unit status
- C_plan = available capacity from the planned outage schedule for the forecast hour
- ratio = C_plan / C_base, if C_base > 0
- C_available = total available unit capacity under the planned outage status

The outage-adjusted plant forecast is:

p_outage = clip(p_clipped * ratio, 0, C_available)

If C_base is zero or no units are available, the plant forecast is set to 0 MW.

Validation/testing outage rule:

For historical validation and testing backtests, actual forecast-day outage status is not used because that would leak information from the forecast day. If archived planned outage schedules are unavailable, the forecast day receives only the latest known unit status before 00:00 of that day. This is treated as the best available pre-forecast outage information.

Operational forecast rule:

For an actual next-day operational forecast, the model can use the planned outage workbook, because it represents information known before issuing the forecast.

Unit-level allocation:

After outage adjustment, the plant-level forecast is distributed only to available units. The allocation uses learned historical unit weights when available, otherwise capacity-based weights are used.

For each unit u:

unit_forecast_u <= unit_capacity_u

If a unit is marked unavailable:

unit_forecast_u = 0

The plant total is recomputed as:

plant_total = sum(unit_forecast_u for all units in the plant)

The cascade total is recomputed as:

total_cascade_generation = sum(plant_total for all plants)

These rules are deterministic and are not tuned using testing data.

17. Unit-level allocation

The RBFNN forecasts plant-level generation first.

The plant-level forecast is then distributed to available units using learned unit weights from historical generation behavior. If learned weights are unavailable, capacity-based allocation is used.

Unit capacity limits are enforced:

- Agus 1 units: 40.0 MW each
- Agus 2 units: 60.0 MW each
- Agus 4 units: 52.7 MW each
- Agus 5 units: 27.5 MW each
- Agus 6 units: 34.5, 34.5, 50.0, 50.0, and 50.0 MW
- Agus 7 units: 27.0 MW each

18. Metrics

The main reported metrics are:

- operational MAPE
- MAE
- RMSE
- R2

Operational MAPE excludes near-zero actual generation values below:

max(1 MW, 1 percent of plant capacity)

This avoids distorted percentage errors during near-zero generation conditions.

MAE, RMSE, and R2 use all rows.

To reproduce the cleaned dataset:

python "Thesis Forecasting/scripts/cell1_clean_data.py"

To retrain and tune all RBFNN plant models:

python "Thesis Forecasting/scripts/cell2_rbfnn.py" --train

To retrain only selected plants:

python "Thesis Forecasting/scripts/cell2_rbfnn.py" --train agus1 agus5

To run strict RBFNN day-ahead validation/testing backtests from saved models:

python "Thesis Forecasting/scripts/cell2_rbfnn.py" --day-ahead-backtest

To generate only the operational next-day RBFNN forecast from saved models:

python "Thesis Forecasting/scripts/cell2_rbfnn.py" --forecast-only

To tune saved day-ahead profile blending on validation predictions only:

python "Thesis Forecasting/scripts/cell2_rbfnn.py" --tune-day-ahead-profile

To regenerate thesis figures and organized metadata workbooks:

python "Thesis Forecasting/scripts/cell4_generate_thesis_and_metrics.py"

21. Reproducibility controls

The workflow sets random seeds for NumPy and TensorFlow:

- np.random.seed(42)
- tf.random.set_seed(42)

K-means center initialization uses:

- random_state = 42
- n_init = 10

Because neural network training can still vary slightly across hardware, TensorFlow versions, and numerical backends, exact bit-for-bit equality is not guaranteed. However, the saved scripts, data, hyperparameter grids, seeds, scalers, metadata files, and model artifacts provide the full procedure needed to reproduce the reported RBFNN methodology and rerun the thesis outputs.
